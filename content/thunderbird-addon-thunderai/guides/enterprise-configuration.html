For administrators deploying ThunderAI across an organization. It covers pre-configuring settings, enforcing them so users cannot change them, distributing a shared set of prompts, replacing the prompts of the special features and choosing their connection, limiting the automatic features to some accounts, and restricting what users can do with prompts and the setup wizard.

No add-on setting needs to be touched on each machine: everything here is driven by Thunderbird's own enterprise policy file.

Enterprise configuration is available from ThunderAI 5.1.0.

Before you start

⚠️ Policies are read only at Thunderbird startup

There is no live reload. Any change to policies.json — including rotating an API key or token — takes effect only after Thunderbird is fully restarted. Users who leave Thunderbird running for days will not pick up a change until they restart.

If you rotate a credential, plan for the window in which running clients still hold the old one.

⚠️ Policy files are world-readable

policies.json must be readable by every user account on the machine, so any local user can read any API key you put in it. It is not a secret store.

Prefer pointing ThunderAI at an internal gateway (via openai_comp_host) that holds the real provider credentials server-side, and put a revocable per-organization token in the policy — not a raw provider key. If you must deploy a provider key directly, use one scoped and rate-limited to this purpose, and rotate it on the assumption it is exposed.

Where policies.json goes

OS Path
Linux /etc/thunderbird/policies/policies.json (recommended)
or <install dir>/distribution/policies.json
Windows C:\Program Files\Mozilla Thunderbird\distribution\policies.json
macOS /Applications/Thunderbird.app/Contents/Resources/distribution/policies.json

On Linux, use /etc/thunderbird/policies/. It lives outside the application directory, so it survives application updates. The distribution directory — the only option on Windows and macOS — sits inside the installation and may be removed or replaced when Thunderbird updates, silently dropping your configuration.

On Windows you can avoid that by using Group Policy / the registry instead of the file, under HKLM\SOFTWARE\Policies\Mozilla\Thunderbird. On macOS, a configuration profile (.mobileconfig) is the equivalent durable option. Both express the same 3rdparty structure shown below.

To verify a policy has loaded, open about:policies in Thunderbird.

Structure

Every ThunderAI setting lives under 3rdparty → Extensions → thunderai@micz.it:

{
  "policies": {
    "3rdparty": {
      "Extensions": {
        "thunderai@micz.it": {
          "connection_type": "openai_comp_api"
        }
      }
    }
  }
}

Policy key names are exactly ThunderAI's own setting names. There is no mapping table and no renaming — see the key reference.

Enforced vs. initial values

Every key you set is enforced by default. The user sees it in the settings, greyed out with a padlock badge reading Managed by <_org_name> (or just Managed), and cannot change it. A banner at the top of the page explains that some settings are managed by the organization.

To supply a starting value the user may then change, add a sibling "<key>:locked": false:

"reply_type": "reply_all",
"reply_type:locked": false
Enforced (default) "<key>:locked": false
User can change it no yes
Control in settings disabled, marked "Managed" with a padlock normal
If the user already set it policy value wins user's value wins
Written to the user's profile never yes, once they change it

That third row matters. An unlocked value is only an initial suggestion: a user who already configured that setting keeps their own value and never sees yours. Use an enforced value if you need it to actually apply everywhere.

Nothing enforced is ever written into the user's profile, so removing a key from the policy cleanly restores whatever the user had before, or the ThunderAI default.

Both kinds of value are shown where the user looks for them. Enforced and initial values appear in the options page and in every feature settings page — including the list fields and the spam filter's address book option, which are locked on their pages like any other control — and they also apply in the API chat window and in the popup.

Policy connection values are not copied into prompts. When a user turns on a specific integration for a single feature (Add Tags, Summarize, Spam Filter…), or sets a connection on a custom prompt, those fields start from the ThunderAI defaults, not from the host, model or key in your policy. A copied value would outlive the policy.

API keys set by policy

An API key supplied by the policy is never displayed in the settings. The field shows a masked placeholder, and from the settings pages the user cannot reveal the key, run the connection test with it, or fetch the model list with it. ThunderAI itself still uses the key normally, in the API chat window and in every feature. Because the model list cannot be fetched with your key, set the model explicitly in the policy (for example openai_comp_model).

An unlocked key ("<key>:locked": false) stays masked until the user types a key of their own, which is then stored and wins, like any other unlocked value.

This keeps the key out of the add-on's pages. It does not make it secret: it is still readable in policies.json — see Before you start.

Worked example

An organization routing all AI traffic through an internal gateway, enforcing the connection and the privacy-relevant settings, suggesting a couple of defaults, and shipping two shared prompts.

Example policies.json 
{
  "policies": {
    "3rdparty": {
      "Extensions": {
        "thunderai@micz.it": {

          "_schema_version": 1,
          "_org_name": "ACME Corporation",
          "_org_id": "acme",

          "connection_type": "openai_comp_api",
          "openai_comp_host": "https://ai-gateway.acme.example/v1",
          "openai_comp_api_key": "acme-gateway-token-REPLACE-ME",
          "openai_comp_model": "gpt-4o",
          "openai_comp_chat_name": "ACME AI",

          "spamfilter": false,
          "add_tags_auto": false,

          "_disable_setup_wizard": true,

          "default_chatgpt_lang": "English",
          "default_chatgpt_lang:locked": false,
          "reply_type": "reply_all",
          "reply_type:locked": false,

          "_org_prompts": [
            {
              "id": "support_reply",
              "name": "Draft support reply",
              "text": "Draft a reply to this customer email. Follow ACME tone of voice: concise, factual, no promises about delivery dates.\n\n{%mail_text_body_or_selected%}",
              "type": "1",
              "action": "1",
              "need_signature": "1"
            },
            {
              "id": "legal_review",
              "name": "Flag legal risk",
              "text": "Review the following text and list any statement that could create a contractual obligation.\n\n{%mail_text_body_or_selected%}",
              "type": "0",
              "action": "0",
              "api_type": "anthropic_api"
            }
          ]

        }
      }
    }
  }
}

What the user sees: the connection is pre-configured and locked, so they are never asked to run the setup wizard — and cannot open it either. The spam filter and auto-tagging are off and cannot be turned on. Language and reply style start at the organization's preference but can be changed. The two ACME prompts appear on the Manage Prompts page with an Organization badge, read-only, and can be Duplicated to make an editable personal version.

Organization prompts

_org_prompts is an array of prompt objects that becomes a shared, read-only prompt set alongside the user's own.

Requires _org_id — lowercase letters, digits and hyphens only, no underscore. It namespaces your prompt ids so they can never clash with ThunderAI's built-ins or with another organization's. Choose it once and never change it: it is part of every prompt id, and changing it makes users lose the menu positions they set.

The final id becomes org_<_org_id>_<id> — so "id": "support_reply" with "_org_id": "acme" is stored as org_acme_support_reply.

Fields

Field Required Notes
id yes unique within the array, no whitespace; prefixed automatically
name yes shown in menus
text yes the prompt; may contain {%placeholder%} tokens
type no "0" always, "1" reading, "2" composing
action no "0" close, "1" reply, "2" substitute text
need_selected no "1" requires a text selection
need_signature no "1" includes the signature
need_custom_text no "1" prompts for extra input
define_response_lang no "1" appends a response-language instruction
use_diff_viewer no "1" offers a diff of the result
api_type no route this prompt to a specific provider

api_type accepts chatgpt_web, chatgpt_api, google_gemini_api, anthropic_api, ollama_api, openai_comp_api. Empty or absent means "use the configured connection".

Behaviour

  • Fully declarative. The policy is the only source of truth. Add, change or remove a prompt and it is reflected at the next Thunderbird start. Users' own prompts are never touched.
  • Read-only, but duplicable. Users cannot edit or delete them, but Duplicate (or Duplicate and edit) makes an ordinary editable personal prompt — unless _disable_prompt_management is on.
  • Users control placement. Menu position and visibility are per-user, set in Menu Order like any other prompt.
  • If a user already has a prompt with the same id, yours takes precedence and theirs is disabled, with an explanation shown on the Manage Prompts page. Their prompt is not deleted and works again if you remove yours.
  • Ship only your prompts. Combine _org_prompts with _disable_default_prompts to take the built-in prompts out of the menus, so users see only the organization set.

If a prompt is rejected

Each prompt is validated independently — one bad entry is skipped, the rest still load. A prompt is skipped if id, name or text is missing or empty, if id is duplicated, or if api_type is not a valid connection type. If _org_id is missing or malformed the whole set is skipped.

Rejections are reported in the Thunderbird Error Console (Tools → Developer Tools → Error Console), prefixed [ThunderAI Logger | mzta-managed]. Check it after changing a policy — these warnings appear whether or not debug logging is on.

Special prompt texts

The special features (Add Tags, Spam Filter, Summarize, Translate, Calendar Event, Task) each run a prompt whose text users can edit on the feature's settings page. _special_prompts_text replaces that text with yours, for every user. For example, you can make the spam filter apply your organization's own criteria: 

"_special_prompts_text": {
  "prompt_spamfilter": "Decide whether this email is spam for ACME. Treat any request to change bank details as spam. Answer only with a JSON object: {\"spamValue\": <0-100>, \"explanation\": \"<one sentence>\"}.\n\n{%mail_html_body%}"
}

Neither of the other mechanisms can do this. These texts are stored with the feature's prompt, not in a preference, and _org_prompts only adds new prompts.

Prompt ids

Key Text
prompt_add_tagsAdd Tags
prompt_spamfilterSpam Filter
prompt_summarizeSummarize, the instruction
prompt_summarize_email_templateSummarize, how each message is presented when several are summarized together
prompt_summarize_email_separatorSummarize, the separator between those messages. Whitespace only is allowed here.
prompt_translate_thisTranslate
prompt_get_calendar_eventCalendar Event
prompt_get_calendar_event_from_clipboardCalendar Event from the clipboard
prompt_get_taskTask

The Calendar Event settings page edits both calendar texts in one field. So a text you set for prompt_get_calendar_event applies to the clipboard variant too, unless the policy also names prompt_get_calendar_event_from_clipboard.

Behaviour

  • Always enforced. There is no initial-value form: "_special_prompts_text:locked" is ignored with a warning.
  • Only the text. Everything else about the feature (its icon, its menu visibility, its connection) stays the user's. To set the connection, use _special_prompts_connection.
  • Read-only on the settings page. The text is shown, marked as managed, and can be selected and copied, but not edited. Save and Reset are disabled.
  • Never written to the user's profile. Removing an entry, or the whole key, restores each user's own text exactly as they had it, or the ThunderAI default.

The response format

Most of these features read the AI's answer as JSON, and the text of the prompt is what asks for that format. A text without it would break the feature for everyone. So a text is rejected if it never names the response fields its feature reads:

Key Must name Must contain
prompt_spamfilter spamValue, explanation a body placeholder, or no placeholder at all
prompt_add_tags tags
prompt_get_calendar_event, …_from_clipboard startDate, endDate, summary {%selected_text%}, {%selected_html%}, a body placeholder, or no placeholder at all
prompt_get_task summary
prompt_translate_this subject, body, status {%mail_html_body%} or {%mail_text_body%}, and {%thunderai_translate_lang%}
prompt_summarize_email_template — a body placeholder, or no placeholder at all
prompt_summarize, prompt_summarize_email_separator — —

Body placeholders: {%mail_text_body%}, {%mail_html_body%}, {%mail_text_body_or_selected%}, {%mail_html_body_or_selected%}. A text with no placeholder at all gets the message appended automatically.

A field name is matched as a whole word, case-sensitive, anywhere in the text. This catches a text rewritten without its output format; it does not check that the format itself is well formed. Start from the ThunderAI default text, shown on each feature's settings page, and keep its format part.

If the value of _special_prompts_text is not an object, the whole key is ignored. Otherwise each entry is checked on its own. An entry is skipped, with a warning, if its key is not one of the ids above, if its value is not a non-empty string, or if it misses a response field: the user's own text then stays in effect. A missing placeholder (the third column) is only a warning, logged at every startup: the text is still enforced, but the message may not reach the AI.

Per-feature connections

Some features can use a connection of their own instead of the main one. In each feature's settings page, users switch on Use a specific integration and pick a provider. _special_prompts_connection lets you set that connection from the policy, feature by feature. For example, you can send spam filtering to a small, cheap model and leave everything else on the main connection.

This connection is stored with the feature's prompt, not in a preference. That is why the ordinary keys cannot set it and this separate key exists. 

"_special_prompts_connection": {
  "spamfilter": {
    "api_type": "openai_comp_api",
    "openai_comp_host": "https://ai-gateway.acme.example/v1",
    "openai_comp_api_key": "acme-gateway-token-REPLACE-ME",
    "openai_comp_model": "gpt-4o-mini",
    "openai_comp_model:locked": false
  }
}

Shape

The value is an object. Each key names a feature, and each value is that feature's connection:

Fields not marked otherwise are strings. That includes the temperatures, *_top_p, *_top_k, google_gemini_thinking_budget and ollama_think: write "0.7", not 0.7. You can leave out any field except api_type. For a field the policy does not set, the feature uses the user's own value if they have one, and otherwise the main connection's value, just as it does without a policy.

Enforced and initial fields

  • api_type is always enforced. "api_type:locked": false is ignored with a warning. Leaving the provider open to change would make no sense while its provider-specific fields are enforced.
  • Every other field is enforced unless you add a sibling "<field>:locked": false, as everywhere else in the policy. An unlocked field works like other initial values, with one difference: it applies only while the user has no value of their own for that field. It is never written to their profile. If the user sets a value of their own, it is kept, and it stays after the policy is removed.
  • A top-level "_special_prompts_connection:locked" is ignored with a warning.

Implied switch and connection type

Each accepted entry also switches the feature to its own connection and sets the connection type, both locked. It is as if the policy also contained: 

"spamfilter_use_specific_integration": true,
"spamfilter_connection_type": "openai_comp_api"

On the feature's settings page, the Use a specific integration switch is on and locked, and the provider select shows your api_type, locked. Enforced fields are locked with the padlock. Unlocked fields stay editable.

If the same policy also sets those two keys explicitly:

Explicit key in the same policy Result
<feature>_use_specific_integration: false, locked or not The connection entry is skipped, with a warning. The explicit switch wins, and the feature uses the main connection.
<feature>_use_specific_integration: true with :locked: false Enforced anyway, with a warning.
<feature>_connection_type that differs from api_type, or is unlocked Replaced by api_type and locked, with a warning.

Allowed types and validation

Every feature accepts the same five api_type values: chatgpt_api, google_gemini_api, anthropic_api, ollama_api and openai_comp_api. chatgpt_web is rejected for every feature. The features cannot run on ChatGPT Web, and their settings pages don't offer it.

Each entry is checked on its own, and one bad entry never stops the rest of the policy:

  • If the value of _special_prompts_connection is not an object, the whole key is ignored.
  • An entry is skipped as a whole if its key is not one of the six features, if it is not an object, or if api_type is missing or not one of the five types above.
  • Every other problem skips only that field, and the rest of the entry applies:
    • a field that belongs to a different provider, for example ollama_host under "api_type": "openai_comp_api";
    • a value of the wrong type. It is not converted: "4096" is not 4096;
    • a value that fails its content rule:
Field Must be
*_host an http:// or https:// URL
*_model not empty
ollama_num_ctx, anthropic_extended_thinking_budget an integer, 0 or more
anthropic_max_tokens an integer, 1 or more
google_gemini_max_output_tokens an integer, 0 or more (0 means not set)
chatgpt_max_output_tokens 0 (not set), or an integer of 16 or more
*_temperature "", or a string holding a number of 0 or more
*_top_p "", or a string holding a number from 0 to 1
*_top_k "", or a string holding an integer, 0 or more
google_gemini_thinking_budget "", or a string holding an integer ("-1" is Gemini's "dynamic")
ollama_think "", "false", "true", or a level in lowercase letters such as "low", "medium", "high", "max". The boolean true/false used before 5.1.0 is still read, with a warning.

"<field>:locked" must be a boolean. Any other value is ignored with a warning, and the field stays enforced. A ":locked" whose field is absent or was rejected is also reported.

The settings pages don't apply these rules to what users type. The policy does, because a typo there breaks the feature for everyone, and users cannot fix it themselves. Every skip is reported in the Error Console and names the feature and the field (see Troubleshooting).

The organization's key

An API key field works like any API key set by policy. The feature uses it normally, but the settings page shows only a masked placeholder. The user cannot reveal the key, fetch the model list with it, or test the connection with it. So set the model in the entry too, for example openai_comp_model. The key is never saved in the user's profile and never included in an export.

Changing and removing it

A change takes effect at the next Thunderbird restart, like every other policy change (see Before you start).

Nothing the policy supplies is written into the user's profile. Removing an entry, or the whole key, restores each user's own per-feature connection exactly as they had it, field by field, including their switch and connection type. A user who had none goes back to the main connection. When the policy replaces a value a user had stored, a warning is logged at startup. It names the feature and the field, never the value.

Limiting features to some accounts

The automatic spam filter and automatic Add Tags can be limited to some accounts. Users choose them with checkboxes on the feature's settings page, stored in spamfilter_enabled_accounts and add_tags_enabled_accounts. Those two keys cannot be set by policy: they hold account identifiers that Thunderbird assigns separately in each profile, so no single value would be right on every machine.

Use spamfilter_enabled_accounts_match and add_tags_enabled_accounts_match instead. They name accounts by what is the same everywhere, and ThunderAI finds the matching accounts in each profile: 

"spamfilter_enabled_accounts_match": [
  "support@acme.example",
  "@sales.acme.example",
  "local"
],
"add_tags_enabled_accounts_match": ["@acme.example"]
Entry Matches
user@acme.example an account with an identity of that address
@acme.example or *@acme.example an account with an identity in that domain
local Local Folders
  • Entries are case-insensitive. An account matches when any of its identities does.
  • RSS feed accounts are never matched.
  • An address with a + tag (user+tag@acme.example) is not accepted. Use the domain form to cover it.
  • Only the automatic runs are limited. Running the feature from the menu on a message works as without a policy.
  • Always enforced. ":locked": false is ignored with a warning: there is no control the user could change the value with.
  • A list that matches nothing means no account, not every account. A warning is logged when it happens. An empty array ([]) in the policy is different: it is the same as leaving the key out.
  • Accounts are matched again each time new mail is processed, so an account added after startup is picked up without a restart.

On the feature's settings page the account checkboxes show the matched accounts, disabled and marked as managed, with a note explaining it. The user's own selection is never changed: removing the key restores it.

Each entry is checked on its own: an entry that is not one of the forms above (including one that is not a string) is skipped with a warning naming its position, and the others still apply. Unlike the other list keys, one bad entry does not discard the whole list. That would fall back to the user's selection, perhaps every account, for a key whose job is to limit where mail is sent. For the same reason, a list whose entries are all invalid is kept as an empty list: no account.

Restrictions

Restrictions are policy-only switches that take something away instead of setting a value. They have no counterpart in the settings, so the :locked convention does not apply to them. 

"_disable_prompt_management": true,
"_disable_default_prompts": true,
"_disable_setup_wizard": true

A restriction is either on (true) or off (false, the same as leaving it out). Any other value — including the string "true" — is ignored with a warning and the restriction stays off. A policy that sets only restrictions still counts as active: users see the managed banner and an explanation next to every disabled control.

Key What the user loses What keeps working
_disable_prompt_management Creating, duplicating, importing and exporting prompts. Their own existing prompts become read-only and disappear from the menus. Built-in and organization prompts, fully usable. The user's prompts are never deleted: they stay listed (read-only, with an explanation) and come back exactly as they were when the restriction is lifted.
_disable_default_prompts The ThunderAI built-in prompts, in every menu and in the popup. They stay listed, dimmed and explained, on the prompt pages. The special features — Add Tags, Summarize, Translate, Spam Filter, Calendar Event, Task — plus the user's own prompts and the organization's. Menu positions and custom icons of the built-ins are kept.
_disable_setup_wizard The setup wizard: its buttons in the options page are disabled, the welcome-page banner is hidden, and opening the wizard by its URL shows Setup wizard unavailable. Everything else. In the popup, the "run the setup wizard" link is replaced by a note that the connection is configured centrally.

The first two are independent and can be combined: they cover different prompts (the user's own and the built-in ones), and each shows its own explanation.

Export is disabled on purpose under _disable_prompt_management: an exported file carries the prompt texts and, with include API settings, can carry provider credentials too.

_disable_setup_wizard only makes sense together with an enforced connection (connection_type and its provider settings). On its own it just leaves users with no guided way to configure ThunderAI. Custom data placeholders are not covered by any restriction.

Settings that require a browser permission

⚠️ A policy can switch these features on, but cannot grant their permission

Two ThunderAI features need an optional permission that the add-on can only request interactively, when the user turns the feature on in its settings page. A policy value does not go through that path: setting the key to true switches the feature on but does not grant the permission. The feature then appears enabled and does nothing until the permission has been granted.

Key Permission Settings page Without the permission
get_calendar_event_from_clipboard clipboardRead Calendar Event The "calendar event from clipboard" menu item is shown, but cannot read the clipboard: using it only shows the error Could not read clipboard. Please check permissions.
spamfilter_skip_addressbook addressBooks Spam Filter The spam filter cannot check whether a sender is in the user's address books, so those senders are not skipped and are analyzed like any other. Nothing is reported to the user. Note that this key defaults to true, so this applies even if you leave it out of the policy.

What you can do

  1. Grant the permission in advance, if your deployment method allows it. Thunderbird's ExtensionSettings policy, as documented in the Thunderbird policy templates, controls how an add-on is installed and updated, but lists no setting to pre-grant an add-on's optional permissions. This has not been verified for every Thunderbird version: check the templates for the version you deploy. If your tooling can grant the permission some other way, the feature works as soon as it is granted.
  2. Otherwise, ask users to grant it once. Each user opens the ThunderAI settings page listed above and turns the option on, then accepts the permission prompt. The prompt appears only when the option is switched on: if it already shows as on, the user switches it off and on again. This needs a control the user can change. If the key is locked by the policy, the control is disabled and the prompt cannot be triggered from there. In that case either set the key with "<key>:locked": false, so the user can grant the permission, or leave the key out of the policy.
  3. Check the result. Keys that ThunderAI rejects are reported in the Thunderbird Error Console (Tools → Developer Tools → Error Console, filter on ThunderAI), even with debug logging off — look there first. A missing permission, though, is not reported: the key is valid, it is the permission that is absent. Confirm it on a test machine using the symptom in the table above.

For example, both features on, as initial values the user can change to grant the permission:

"get_calendar_event_from_clipboard": true,
"get_calendar_event_from_clipboard:locked": false,
"spamfilter_skip_addressbook": true,
"spamfilter_skip_addressbook:locked": false

Keep in mind that an unlocked value is only a starting point: a user who already set the option keeps their own value, and can turn the feature off again (see Enforced vs. initial values).

As with every policy change, this takes effect only at the next Thunderbird restart — see Before you start.

Key reference

Every key below is a ThunderAI setting name, used verbatim as the policy key. Values must match the type shown: a wrong type is ignored with a warning and is not coerced — "true" is not true, and "70" is not 70.

Array keys (add_tags_exclusions, spamfilter_skip_addresses, spamfilter_block_addresses, summarize_auto_senders_list) must contain only strings. A single element of another type makes ThunderAI ignore the whole value, with a warning — it is not filtered out. The account lists (*_enabled_accounts_match) are the exception: they are checked entry by entry, see Limiting features to some accounts.

Values the add-on cannot use

A value of the right type is also checked against what the setting accepts, and rejected the same way — ignored with a warning naming the key, never adjusted:

Keys Must be
connection_type one of the connection types listed in the key reference. Not "", which means "not configured".
<feature>_connection_type one of the five API types. Not chatgpt_web: the features cannot run on it.
reply_type, diff_granularity, summarize_display_mode, summarize_auto, translate_auto one of the values listed for the key: the choices its settings page offers
every number an integer, 0 or more. spamfilter_threshold: 0 to 100. add_tags_maxnum, summarize_max_messages, max_prompt_length, batch_max_concurrency: 1 or more.
calendar_timezone "", or a time zone name as the Calendar Event settings list it, such as "Europe/Rome" (case-sensitive)
the provider keys (openai_comp_host, ollama_num_ctx, chatgpt_temperature…) the same rules as the fields of a per-feature connection: hosts are http(s):// URLs, models are not empty, temperatures are strings holding a number… See the rules table.

Free-text keys (languages, signature name, system prompts…) accept any string. Provider-specific choices such as chatgpt_reasoning_effort or anthropic_effort are not checked: the values each provider accepts change with its models. The exceptions are the ChatGPT choices the settings page offers as a fixed list (chatgpt_verbosity, chatgpt_text_format, chatgpt_truncation, chatgpt_service_tier): those must be one of its values, see the rules table.

One rule spans two keys. An automatic summary is always shown inline. So when the policy sets summarize_auto to 2 or 3 and also sets summarize_display_mode, the display mode becomes "inline", with a warning, and takes the lock of summarize_auto: enforced if that is enforced, an initial value if it has ":locked": false.

Troubleshooting

Open about:policies to confirm Thunderbird loaded the file at all. If ThunderAI's settings are not listed there, the problem is the file's location or its JSON syntax, not ThunderAI.

Open the Error Console (Tools → Developer Tools → Error Console) and filter on ThunderAI. Rejected keys and prompts are reported there, each naming what was wrong. These warnings are not gated on debug logging.

Symptom Likely cause
Nothing applied at all File in the wrong place, or invalid JSON. Check about:policies.
One key ignored, warning about its type Value type does not match — "true" is not true, "70" is not 70.
One key ignored, warning that it "must be" something The type is right but the value is not usable: not one of the listed values, out of range, a host that is not a URL, an unknown time zone. See Values the add-on cannot use.
A list key ignored as a whole One of its elements is not a string. Array keys must contain only strings.
One key ignored, "cannot be set by policy" It is in the excluded list above.
Settings still editable The key has "<key>:locked": false, or you are looking at a key you did not set.
A change did nothing Thunderbird was not restarted. Policies are read only at startup.
Organization prompts missing _org_id missing or contains an underscore/uppercase — the whole set is then skipped.
One prompt missing Missing id, name or text, a duplicate id, or an invalid api_type.
A special prompt text not applied Unknown prompt id, an empty text, or a text that does not name the response fields its feature reads (for example spamValue). The user's own text stays in effect. See Special prompt texts.
A special prompt text applied, but the feature ignores the message The text has placeholders but none that brings in the message (or, for Translate, no {%thunderai_translate_lang%}). A warning is logged at every startup.
Automatic spam filter or Add Tags runs on no account *_enabled_accounts_match matches no account in that profile, or all its entries were rejected. See Limiting features to some accounts.
Summaries shown inline although the policy sets webchat Expected: summarize_auto is 2 or 3, and automatic summaries are always inline.
A per-feature connection ignored as a whole Unknown feature key, a missing api_type, chatgpt_web, or the same policy sets <feature>_use_specific_integration to false. See Per-feature connections.
One field of a per-feature connection ignored It belongs to a different provider, has the wrong type (temperatures are strings), or fails its content rule, such as a host that is not an http(s):// URL.
A restriction has no effect The value is not the boolean true — "true" or 1 is ignored and the restriction stays off.
Users' own prompts vanished from the menus _disable_prompt_management is on. The prompts are not deleted: they are still listed read-only and return when the restriction is removed.
Built-in prompts vanished from the menus _disable_default_prompts is on. Special features such as Summarize or Add Tags are not affected.
An unlocked value did not apply The user had already set that preference; their value wins. Enforce it instead.
Calendar from clipboard or address book skipping enabled, but not working The feature's permission was never granted. See Settings that require a browser permission.
Calendar Event ignores the message body, warning about calendar_no_selection The option is on but the Calendar Event prompt has neither {%mail_text_body_or_selected%} nor {%mail_html_body_or_selected%}.
Users cannot test the connection or fetch models Expected when the API key comes from the policy. Set the model in the policy. See API keys set by policy.

Notes

  • ThunderAI requests no additional permissions for any of this. Two features have a permission of their own that a policy cannot grant — see Settings that require a browser permission.
  • With no policy installed, ThunderAI behaves exactly as it does for any individual user.
